# Dashboard design direction

Phase 1 deliverable. Written **before** any component code, per the task brief.
This note explains the visual decisions and their reasons so a later change is
an argument, not a preference.

The companion validated screen is `dashboard/design/queue_preview.html`
(generated by `dashboard/design/build_preview.py` from **real Supabase rows** —
it is a design probe, not a mock; see "Why the sketch uses real rows" below).

> **Note on process.** The brief says to read the `frontend-design` skill first.
> That skill is not installed in this environment (no `.claude/skills/`, nothing
> under `~/.claude/skills/`, no plugin providing it). The `dataviz` skill **is**
> installed and was read before any chart colour was chosen; every palette
> decision below that touches a chart mark was run through its
> `scripts/validate_palette.js` and the output is quoted verbatim.

---

## 1. Register

Cortech writes technical and EOI proposals for UNICEF, UNDP, DRC and GIZ. The
people using this tool spend their day inside donor ToRs and evaluation grids.
The dashboard should feel like it belongs next to those documents.

Concretely, that rules out three defaults:

- **No SaaS landing-page vocabulary.** No gradient hero, no drop-shadowed
  feature cards, no rounded-2xl everything, no illustrative iconography.
- **No generic admin panel.** No dark sidebar with coloured pill badges, no
  "Dashboard / Analytics / Settings" scaffold inherited from a template.
- **No dashboard-as-scoreboard.** Big green numbers going up is the wrong
  emotional register for a tool whose headline number is a *heuristic* and whose
  most common honest answer is "not enough data."

What it should feel like: a well-set internal report that happens to be live.
Quiet, dense, typographic, with the machinery visible when you look for it.

## 2. Typography

| Role | Face | Why |
|---|---|---|
| UI chrome, labels, tables, numbers | **Inter** | Large x-height and tight, even colour at 11–13px, which is the size most of this interface lives at. Ships `tabular-nums`, which the score columns need. |
| Evidence prose, tender titles, `why` strings | **Source Serif 4** | A text serif designed for on-screen reading. It marks a hard boundary: *serif means this text came out of a document or a model, sans means the application is talking.* A reviewer can tell at a glance whether they are reading Cortech's tool or a tender's words. |
| URLs, hashes, `execution_id`, `content_hash`, claim tokens | **IBM Plex Mono** | Identifiers must be comparable character-by-character and safe to select. |

Three families is defensible only because each has a job the others can't do.
The serif/sans split is the load-bearing one — it is the same idea as the
repo's `wrap_untrusted()` boundary, expressed typographically.

All three are self-hosted as woff2 under `dashboard/static/fonts/` with a full
system fallback stack. Reasons: an internal BD tool should not make a
third-party request on every page load, and the tool must render correctly on a
restricted network. If the fonts fail to load, the fallback stack keeps the
serif/sans distinction (`ui-serif, Georgia` vs `ui-sans-serif, Segoe UI`).

Type scale is a 1.2 ratio on an 8px rhythm: 11 / 12 / 13 / 16 / 19 / 23 px.
Eyebrow labels are 11px, uppercase, `letter-spacing: 0.08em` — inherited from
the existing review email, which the team already reads daily.

## 3. Colour

### 3.1 The dashboard inherits the existing Cortech identity

`reporting/email_report.py` already defines a coherent palette that the BD team
sees every time the agent drafts something: navy `#1F3864`, brass `#C4A35A`,
warm paper `#F7F4EE`, warm ink `#1C1914`, hairline `#E6E1D6`. That is Cortech's
de-facto identity, and inventing a second one for the dashboard would make the
email and the tool look like two different companies' products.

So the dashboard reuses it rather than replacing it. Two corrections were made,
both because the numbers said so, not because of taste:

| Token | Existing use | Measured | Change |
|---|---|---|---|
| `#8A7A5A` | 10–11px uppercase eyebrow labels in the review email | **3.82:1** on paper — fails AA for text that size | Demoted to rules/separators only. Eyebrow labels in the dashboard use `#6B6458` (**5.33:1**). |
| `#C4A35A` brass | used as link text in the email | **2.19:1** on paper | Never text in the dashboard. Brass is a rule, a mark fill, and the focus ring only. |
| `#dc3545` / `#28a745` / `#f0a500` | legacy Bootstrap status hexes, used inconsistently alongside the refined palette | — | Not carried over. The dashboard uses the `dataviz` fixed status palette (§3.3). |

The email itself is not changed — that is outside this phase's scope. The
corrections apply to the dashboard only, and are flagged here so the email can
be brought in line later.

### 3.2 The important decision: colour encodes *evidence status*, not sentiment

The single largest failure mode for this UI is that a reviewer reads a number as
more certain than it is. Every colour rule below exists to prevent that.

**Missing data is grey, never red.**

```
VERIFIED              #006300   6.87:1   evidence located in the source text
INFERRED              #8A6A12   4.61:1   partial / fuzzy match
UNKNOWN               #6B6458   5.33:1   not extracted — and deliberately neutral
INSUFFICIENT DATA     #6B6458   5.33:1   same token as UNKNOWN, on purpose
```

`UNKNOWN` sharing a token with the ordinary secondary ink is the point. An
un-extracted budget is not a problem with the opportunity; colouring it red
would push a reviewer to read absence as a negative signal about the bid. This
is the rule most likely to be "improved" by a later redesign, so: **the absence
of data must never be more visually salient than the presence of it.**

**BID / WATCH / NO-BID get weight and shape, not hue.**

In the lists and the detail header these are typographic chips, not coloured
badges: BID is a filled navy chip, WATCH is an outlined chip, NO-BID is a plain
grey chip. `bid_scorer.py` v1.0.0 is a deterministic weighted heuristic over a
JSON weights file; rendering NO-BID in red would let that weights file look like
a verdict. (In *charts*, where a legend is present and the categories are being
counted rather than judged, an ordered ramp is used instead — see §3.4.)

**Red is reserved for "the machine stopped."** `failed`, `dead_letter`, and
spend-cap halt. It never appears because a bid scored badly.

### 3.3 Status palette (machine states only)

Taken unchanged from the `dataviz` skill's fixed status palette, which is
explicitly never themed:

| State | Token | Meaning in this system |
|---|---|---|
| `dead_letter` | `#d03b3b` critical | Drafting exhausted `MAX_DRAFT_FAILURES = 3` (ADR 011) |
| `failed` | `#ec835a` serious | Retryable. Stage and checkpoint preserved; next claim resumes |
| spend-cap halt | `#fab219` warning | `MAX_RUN_COST_USD` reached (ADR 012). Retryable, does **not** count as a draft failure |
| `completed` | `#0ca30c` good | Agent work finished at `drafted`, or a terminal skip |
| `cancelled` | `#fab219` warning | A person stopped the run via the dashboard. Amber, like a cap halt, because it is the *same* mechanism and equally resumable — and never red, because nothing broke |

Two of these are below 3:1 on the light surface by design; the mitigation is the
skill's icon + label pairing, which this UI follows — every state chip carries
its literal ledger word (`dead_letter`, `failed`) as text. No state is ever
communicated by colour alone.

### 3.4 Chart colour

Two sequential contexts appear on the Portfolio view, so per the skill's rule
the second takes the next brand hue.

**Pipeline stages** (`discovered → extracted → scored → drafted`) are genuinely
*ordered*, so they are an ordinal ramp in the brand navy hue, not a categorical
set:

```
$ node scripts/validate_palette.js "#6291e3,#406cbb,#1e4994,#002972" \
      --ordinal --mode light --surface "#FFFFFF"
  [PASS] Lightness monotone     steps read light→dark
  [PASS] Adjacent ΔL            all gaps >= 0.06
  [PASS] Light-end contrast     #6291e3 at 3.14:1 vs surface
  [PASS] Single hue             hue spread 0°
  → ALL CHECKS PASS        exit=0
```

**BID / WATCH / NO-BID** is also ordered (descending pursuit intent), which
conveniently solves the "don't hue-code NO-BID as bad" problem — it becomes the
lightest step of one ramp rather than a red category. It takes the brass hue:

```
$ node scripts/validate_palette.js "#c3a35f,#947630,#705300" \
      --ordinal --mode light --surface "#FFFFFF"
  [PASS] Lightness monotone     steps read light→dark
  [PASS] Adjacent ΔL            all gaps >= 0.06
  [PASS] Light-end contrast     #c3a35f at 2.41:1 vs surface
  [PASS] Single hue             hue spread 1°
  → ALL CHECKS PASS        exit=0
```

The light end is 2.41:1, under 3:1, so the skill's **relief rule** applies and
is mandatory, not optional: every bar carries a visible direct label and the
same counts are available as a table. This is implemented, not aspirational.

**Won / Lost / Unknown is not a chart.** The current census is 123 WON, 0 LOST
(ADR 010) and `win_loss_memory` does not exist. A pie or bar of that is a lie
told with geometry. It renders as stat tiles with the UNKNOWN denominator stated
in words.

### 3.5 No dark mode in v1

Deliberate, not an omission. A second palette doubles the surface on which an
evidence-status colour can drift out of contrast, and §3.2 is the part of this
system least able to survive a sloppy second theme. One correct palette first.

## 4. Density and whitespace

This is a data-heavy tool that has to stay legible. Four rules do most of the
work:

1. **Rules, not cards.** Rows are separated by 1px `#E6E1D6` hairlines, not by
   boxed cards with shadows. Twenty cards on a page create eighty competing
   edges; twenty rules create one reading axis. This is the single biggest lever
   for "dense but uncluttered," and it is also why the page can afford to be
   dense at all.
2. **Whitespace is spent on the left.** A wide left gutter with small-caps
   section labels gives a dense table a spine. Content is capped at 1200px;
   evidence prose is capped at 70ch regardless of viewport.
3. **Progressive disclosure by row, not by page.** The queue row shows only what
   drives the decision to click: title, client, stage, recommendation, deadline,
   action. Factor tables, evidence sentences and provenance live on the detail
   view. No hover cards, no modals, no accordions in lists — a reviewer should
   never have to hover to find out what something is.
4. **8px grid, 44px minimum row height.** Comfortable pointer target, and ~18
   rows visible on a laptop without scrolling.

Numbers use `font-variant-numeric: tabular-nums` with a fixed decimal column, so
scanning a score column is a vertical movement rather than a zig-zag.

## 5. The one component that enforces "never invent data"

There is a single shared value primitive. Every field on every screen goes
through it:

```jinja
{% macro value(v, missing="—", why="") %}
  {% if v is none or v == "" %}
    <span class="v-missing" title="{{ why }}">{{ missing }}</span>
    {% if why %}<span class="v-why">{{ why }}</span>{% endif %}
  {% else %}
    <span class="v">{{ v }}</span>
  {% endif %}
{% endmacro %}
```

`v-missing` is grey em-dash; `v-why` carries the literal reason from the data
(`not yet scored`, `INSUFFICIENT DATA`, `UNKNOWN`, `no ledger row`). There is no
CSS path that renders a missing value as anything that could be mistaken for a
real one — no `0`, no `N/A` styled like a figure, no zero-height bar.

Score provenance is attached in the same primitive rather than left to each
template: any rendering of WIN PROBABILITY emits its heuristic label inline, so
a future layout change cannot separate the number from its caveat.

```
WIN PROBABILITY   58   heuristic (see docs/SCORING_MODEL.md)
calibrated P(win)  —   INSUFFICIENT DATA — 123 WON / 0 LOST (ADR 010)
```

The calibrated field is **shown and empty**, never hidden. Hiding it for visual
tidiness would let a later reader assume it doesn't exist.

## 6. Why the sketch uses real rows

Constraint 1 of the brief is "never invent data." A design sketch populated with
`Lorem Tender for WASH Services — $250,000 — 87% win` would be the exact
failure the constraint exists to prevent, and it would also validate the wrong
thing: invented rows are uniformly tidy, and this dataset is not. The real data
has `title = "Unknown"`, 1212 cache rows against 8 ledger rows, `analysis_json`
populated 0/1212, and `calibrated_win_probability` null everywhere.

The preview is therefore generated from live Supabase reads. It is what forced
the "no ledger row" and "not yet scored" states into the design at Phase 1
rather than Phase 3.

## 7. What rendering against real rows changed

Recorded so the next person knows these were findings, not preferences.

1. **Absence was louder than presence.** The first render spelt out "no
   ledger row — never claimed for processing" in four columns of six rows.
   Correct, and unreadable — it inverted §4. Tables now use a terse variant
   (em dash, reason in the tooltip); the detail view keeps the full reason
   because there is one of each.
2. **Column geometry.** Without fixed columns, long scraped titles and long
   provenance strings squeezed the title column to ~100px. `table-layout:
   fixed` with the title column taking the slack.
3. **Eyebrow notes inherited uppercase.** The section label's
   `text-transform` cascaded into its explanatory paragraph. Reset.
4. **`"Unknown"` is not a title.** Discovery writes the literal string when
   it has none; the cache rows rendered it as a real title. It is now an
   absence.
5. **`completed` + `discovered` is not pending work.** Those rows are
   terminal skips (consultancy FALSE / NO-BID). They got their own section
   with that explanation rather than sitting in a "needs drafting" list.
6. **Commercial value has no `score` key.** It is `contract_value_usd`; the
   first render showed a real extracted budget as "not available" — the
   inverse of this repo's usual failure, but a failure. Read by key list now.

## 8. What this direction is not

Not a design system, not a component library, not themeable. It is one screen
family for one internal tool, sized to the problem.
